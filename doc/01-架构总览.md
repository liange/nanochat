# 01 - 架构总览

## 1. 项目定位

nanochat 是一个**极简的全栈 LLM 训练框架**，目标是在**单 GPU 节点**上以 **<$100** 的成本训练出 GPT-2 级别能力的大语言模型，并能在类 ChatGPT 的 Web UI 中与它对话。

所谓「全栈」，是指它覆盖了 LLM 的全部主要阶段：

```
tokenization → pretrain → SFT → RL → eval → inference → chat UI
```

这些阶段对应的入口脚本都放在 `scripts/` 目录，核心逻辑放在 `nanochat/` 核心库中（见 `README.md:136` 的文件结构说明）。

设计上的核心取舍是：**宁可精简、可读、可 fork，也不做框架化**。仓库刻意避免庞大的配置对象、模型工厂、冗长的 if-else 分支，追求「单一、内聚、最小、可读、可 hack」的强基线代码库（见 `README.md:193`）。

## 2. 目录结构


## 3. 核心设计概念

### 3.1 单一复杂度旋钮 `--depth`

这是 nanochat 最核心的设计哲学：**用户只需要指定 Transformer 的层数 `--depth`**，其余所有超参（模型宽度、head 数、学习率、训练步数、batch size、weight decay 等）都由代码根据 scaling laws 自动推导，使训练结果接近 compute-optimal。

- 入口在 `scripts/base_train.py:50`，默认 `--depth=20`。
- 模型宽度推导：`base_dim = depth * aspect_ratio`，再向上取整到 `head_dim` 的倍数，`num_heads = model_dim // head_dim`（`scripts/base_train.py:133`）。
- GPT-2 能力大约落在 `d24–d26`（`README.md:97`）。
- 任何代码改动都必须对**所有 depth** 成立，不能只针对某一档（`AGENTS.md`）。

### 3.2 精度管理：不使用 autocast

nanochat **不使用 `torch.amp.autocast`**，而是通过 `nanochat/common.py:31` 中的全局 `COMPUTE_DTYPE` 显式管理精度：

| 硬件 | 默认 dtype | 原因 |
|------|-----------|------|
| CUDA SM 80+（A100/H100） | `bfloat16` | 原生 bf16 tensor core |
| CUDA SM < 80（V100/T4） | `float32` | 无 bf16，可用 `NANOCHAT_DTYPE=float16`（需 GradScaler） |
| CPU / MPS | `float32` | 无低精度 tensor core |

- 可用环境变量 `NANOCHAT_DTYPE` 覆盖（`nanochat/common.py:17`）。
- master 权重保持 fp32（为优化器精度），自定义 `Linear`（`nanochat/gpt.py:45`）在前向时把权重 cast 到 `COMPUTE_DTYPE`；embedding 直接以 `COMPUTE_DTYPE` 存储省显存（`nanochat/gpt.py:263`）。
- 这套机制等价于 autocast 的混合精度收益，但对「什么在什么精度下运行」有完全显式的控制（`README.md:104`）。
- 细节见 [04-模型与训练机制](04-模型与训练机制.md)。

### 3.3 分布式（DDP）：torchrun 与梯度累积无缝切换

- 是否分布式由 `torchrun` 注入的环境变量决定（`nanochat/common.py:136` 的 `is_ddp_requested`）。
- `compute_init`（`nanochat/common.py:173`）负责设备分配、`nccl` 进程组初始化、设置 seed 与 tf32。
- **省略 `torchrun` 时自动切到单 GPU + 梯度累积**，结果基本一致（`README.md:71`）。
- 优化器有单机版 `MuonAdamW` 与分布式版 `DistMuonAdamW`（`nanochat/optim.py:154 / :299`），分布式版采用 ZeRO-2 风格的 reduce_scatter / all_gather 通信，3 阶段异步重叠（见 [04](04-模型与训练机制.md)）。

### 3.4 Flash Attention 3 / SDPA 自动切换

`nanochat/flash_attention.py` 暴露一个与 FA3 API 完全一致的 `flash_attn` 命名空间，内部根据硬件自动选择：

- 仅 **Hopper（sm90）+ bf16** 时用 FA3（`nanochat/flash_attention.py:48`）。
- 其余情况（Blackwell / Ada / MPS / CPU，或 fp16/fp32）回退到 PyTorch SDPA（`nanochat/flash_attention.py:69`）。
- 滑动窗口注意力（`--window-pattern`，默认 `SSSL`）依赖 FA3；无 FA3 时 SDPA 对滑动窗口支持差，建议 `--window-pattern L`（`scripts/base_train.py:114`）。

### 3.5 `NANOCHAT_BASE_DIR` 环境变量

所有中间产物（数据分片、tokenizer、checkpoint、报告）的存放根目录由 `NANOCHAT_BASE_DIR` 决定，默认 `~/.cache/nanochat`（`nanochat/common.py:70`）。

## 4. 关键约定

- **入口都是 module**：训练/评估/对话均须从仓库根运行，如 `python -m scripts.base_train`、`torchrun ... -m scripts.base_train`（`AGENTS.md`）。
- **`--` 分隔符**：`torchrun ... -m scripts.base_train -- --depth=24` 中 `--` 把 torchrun 自身参数与脚本参数隔开（`AGENTS.md`）。
- **`print0` / `log0`**：只在 rank 0 输出/落盘，避免多 rank 重复（`nanochat/common.py:117`、`nanochat/checkpoint_manager.py:19`）。
- **推理引擎与训练前向必须一致**：`engine.py` 基于 KV cache，只处理 token id 序列、不碰 tokenization；修改模型前向时务必同步 KV cache 路径（`AGENTS.md`），仓库有对照测试（`tests/`）守住。
- **仓库只跑 pytest**，无 lint / typecheck / formatter（`AGENTS.md`）。

## 5. 端到端入口

完整复现 GPT-2 级模型的参考脚本是 `runs/speedrun.sh`（8×H100，约 3 小时，`runs/speedrun.sh:1`），它依次执行：

1. `nanochat.report reset` —— 重置训练报告
2. `nanochat.dataset -n 8` —— 下载少量分片用于训练 tokenizer
3. `scripts.tok_train` / `scripts.tok_eval` —— 训练并评估 tokenizer
4. （后台）`nanochat.dataset -n 170` —— 下载更多分片用于预训练
5. `scripts.base_train --depth=24 --target-param-data-ratio=8 --fp8` —— 预训练
6. `scripts.base_eval` —— 评估 base 模型
7. 下载 identity_conversations.jsonl —— 注入人格
8. `scripts.chat_sft` / `scripts.chat_eval -i sft` —— SFT 微调并评估
9. `nanochat.report generate` —— 生成最终报告

CPU/MPS 演示用 `runs/runcpu.sh`。完整流程的数据流与各阶段细节见 [02-核心流程](02-核心流程.md)。
