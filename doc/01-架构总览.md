# 01 - 架构总览

## 1. 项目定位

nanochat 是一个**极简的全栈 LLM 训练框架**，目标是在**单 GPU 节点**上以 **<$100** 的成本训练出 GPT-2 级别能力的大语言模型，并能在 CLI 中与它对话。

所谓「全栈」，是指它覆盖了 LLM 的主要阶段：

```
tokenization → pretrain → SFT → RL → base eval → chat eval → inference → CLI
```

这些阶段对应的入口脚本都放在 `scripts/` 目录，核心逻辑放在 `nanochat/` 核心库中（见 `README.md#File structure`）。

设计上的核心取舍是：**宁可精简、可读、可 fork，也不做框架化**。仓库刻意避免庞大的配置对象、模型工厂、冗长的 if-else 分支，追求「单一、内聚、最小、可读、可 hack」的强基线代码库（见 `README.md#Contributing`）。

## 3. 核心设计概念

### 3.1 单一复杂度旋钮 `--depth`

这是 nanochat 最核心的设计哲学：**用户只需要指定 Transformer 的层数 `--depth`**，其余所有超参（模型宽度、head 数、学习率、训练步数、batch size、weight decay 等）都由代码根据 scaling laws 自动推导，使训练结果接近 compute-optimal。

- 入口参数在 `scripts/base_train.py:CLI arguments`，默认 `--depth=20`。
- 模型宽度推导（`scripts/base_train.py:build_model_meta`）：

  ```
  base_dim  = depth * aspect_ratio          # --aspect-ratio 默认 64
  model_dim = ceil(base_dim / head_dim) * head_dim   # --head-dim 默认 128
  num_heads = model_dim // head_dim
  ```

  `model_dim` 向上取整到 `head_dim` 的整数倍，既保证 head 维度整除，也满足 FA3 要求 head_dim 被 8 整除。**注意 `--head-dim` 也是可调旋钮**，不是硬编码。
- GPT-2 能力大约落在 `d24–d26`（`README.md#Time-to-GPT-2 Leaderboard`）。
- 任何代码改动都必须对**所有 depth** 成立，不能只针对某一档（`AGENTS.md`）。

### 3.2 精度管理：不使用 autocast

nanochat **不使用 `torch.amp.autocast`**，而是通过 `nanochat/common.py#COMPUTE_DTYPE` 中的全局 `COMPUTE_DTYPE` 显式管理精度：

| 硬件 | 默认 dtype | 原因 |
|------|-----------|------|
| CUDA SM 80+（A100/H100） | `bfloat16` | 原生 bf16 tensor core |
| CUDA SM < 80（V100/T4） | `float32` | 无 bf16，可用 `NANOCHAT_DTYPE=float16`（需 GradScaler） |
| CPU / MPS | `float32` | 无低精度 tensor core |

- 可用环境变量 `NANOCHAT_DTYPE` 覆盖（`nanochat/common.py#_detect_compute_dtype`）；`COMPUTE_DTYPE_REASON` 记录了选择原因，训练启动时会打印。
- master 权重保持 fp32（为优化器精度），自定义 `Linear`（`nanochat/gpt.py#Linear`）在前向时把权重 cast 到输入 dtype；embedding 直接以 `COMPUTE_DTYPE` 存储省显存（`nanochat/gpt.py#init_weights`）。
- 这套机制等价于 autocast 的混合精度收益，但对「什么在什么精度下运行」有完全显式的控制（`README.md#Precision / dtype`）。

### 3.3 分布式（DDP）：torchrun 与梯度累积无缝切换

nanochat **不使用 `torch.nn.parallel.DistributedDataParallel`**，而是把梯度同步内建进优化器的 `step()`：

- 是否分布式由 `torchrun` 注入的环境变量决定（`nanochat/common.py#is_ddp_requested`）。
- `compute_init`（`nanochat/common.py#compute_init`）负责设备分配、`nccl` 进程组初始化、设置 seed 与 tf32。
- **省略 `torchrun` 时自动切到单 GPU + 梯度累积**，结果基本一致（`README.md`）。
- 优化器只有**一个类** `MuonAdamW`（`nanochat/optim.py#MuonAdamW`），单机与分布式共用：没有多 rank 进程组时，通信算子全部跳过。分布式下走 ZeRO-2 风格 reduce_scatter / all_gather，3 阶段异步重叠。

> 历史：旧版本有独立的 `DistMuonAdamW` 类。上游已把两者合并为一个类以避免「改了一个忘了改另一个」的 bug，**`DistMuonAdamW` 这个名字已不存在**。

### 3.4 Flash Attention 3 / SDPA 自动切换

`nanochat/flash_attention.py` 暴露一个与 FA3 API 完全一致的 `flash_attn` 命名空间，内部根据硬件自动选择：

- FA3 加载（`nanochat/flash_attention.py#_load_flash_attention_3`）的**实际判定只有一步**：`torch.cuda.get_device_capability()` 的 major 是否为 **9**。
  - `major == 9`（Hopper/sm90）→ 用 `varunneal/flash-attention-3` 内核（注释说它在 H100 上结果更好）；
  - 其他 major → 用 `kernels-community/flash-attn3`，**但先 `has_kernel()` 探测**，取不到就返回 `None`（回退 SDPA）。
- 源码注释说 FA3 内核"currently compiled for Hopper (sm90), Ada (sm89) and Ampere (sm80/sm86)"，**但代码没有按 sm89/sm80/sm86 分支**——那些架构能否用上完全取决于 `kernels-community/flash-attn3` 在你的环境里是否有可用内核。**Blackwell (sm100)** 注释明确说要回退 SDPA（等 FA3 重编译或 FA4）。
- 整个加载包在 `try/except Exception: return None` 里：任何 import/探测失败都静默降级为无 FA3。
- FA3 只支持 bf16；fp16/fp32 在 `_resolve_use_fa3` 里被排除。
- 其余情况（MPS / CPU 等）回退到 PyTorch SDPA（`nanochat/flash_attention.py#_sdpa_attention`）。
- 决策在 `nanochat/flash_attention.py#_resolve_use_fa3` 一次性完成，结果存在 `USE_FA3`；测试可用模块级 `_override_impl` 强制切换。
- 滑动窗口注意力（`--window-pattern`，默认 `SSSL`）**依赖 FA3**；无 FA3 时 SDPA 不支持滑动窗口、会严重拖慢，`scripts/base_train.py` 会打印警告并建议 `--window-pattern L`（`scripts/base_train.py:Flash Attention status`）。

### 3.5 `NANOCHAT_BASE_DIR` 环境变量

所有中间产物（数据分片、tokenizer、checkpoint）的存放根目录由 `NANOCHAT_BASE_DIR` 决定，默认 `~/.cache/nanochat`（`nanochat/common.py#get_base_dir`），目录不存在会自动创建。

## 4. 关键约定

- **入口都是 module**：训练/评估/对话均须从仓库根运行，如 `python -m scripts.base_train`、`torchrun ... -m scripts.base_train`（`AGENTS.md`）。
- **`--` 分隔符**：`torchrun ... -m scripts.base_train -- --depth=24` 中 `--` 把 torchrun 自身参数与脚本参数隔开（`AGENTS.md`）。
- **`print0` / `log0`**：只在 rank 0 输出/落盘，避免多 rank 重复（`nanochat/common.py#print0`、`nanochat/checkpoint_manager.py#log0`）。
- **推理引擎与训练前向必须一致**：`engine.py` 基于 KV cache，只处理 token id 序列、不碰 tokenization；修改模型前向时务必同步 KV cache 路径（`AGENTS.md`）。仓库有两层守护：`tests/test_engine.py` 的 pytest 用例，以及 `nanochat/engine.py` 文件末尾的 `__main__` 内联对照自测。
- **仓库只跑 pytest**，无 lint / typecheck / formatter（`AGENTS.md`）。

## 5. 端到端入口

完整复现 GPT-2 级模型的参考脚本是 `runs/speedrun.sh`（8×H100，约 1.5 小时），它依次执行：

1. `python -m nanochat.dataset -n 8` —— 下载少量分片用于训练 tokenizer
2. **后台**启动 `python -m nanochat.dataset -n 170 &` —— 下载更多分片用于预训练，与 tokenizer 训练并行
3. `python -m scripts.tok_train` / `python -m scripts.tok_eval` —— 训练并评估 tokenizer
4. `wait $DATASET_DOWNLOAD_PID` —— 等下载完成
5. `torchrun ... -m scripts.base_train -- --depth=24 --target-param-data-ratio=8 --device-batch-size=16 --fp8 --run=$WANDB_RUN` —— 预训练
6. `torchrun ... -m scripts.base_eval -- --device-batch-size=16` —— 评估 base 模型
7. `torchrun ... -m scripts.chat_sft -- --run=$WANDB_RUN` —— SFT 微调
8. `torchrun ... -m scripts.chat_eval -- -i sft` —— 评估 chat 模型

脚本最后一行是一句**注释掉的**对话示例 `python -m scripts.chat_cli -p "Why is the sky blue?"`——speedrun 不会自动跑对话，需要你手动执行。

> 注意 speedrun 用了 `--target-param-data-ratio=8`（默认 12）**故意略欠训**以压缩墙钟时间，代价是 val_bpb 略差。`--fp8` 与 `--device-batch-size=16` 都是 H100 上的吞吐取舍。
>
> 脚本开头会 `uv sync --extra gpu` 并 `source .venv/bin/activate`，所以它是设计在**空白节点**上端到端跑通的。
>
> **关于耗时**：`runs/speedrun.sh` 头部注释与本文档都写 ~1.5 小时，而根 `README.md` 的 Leaderboard 段落写的是 ~2 小时 / ~$48。两处口径不一致（可能分别对应「纯训练时间」与「含 tokenizer 与评估的全程」），引用时请说明来源。

CPU/MPS 演示用 `runs/runcpu.sh`。完整流程的数据流与各阶段细节见 [02-核心流程](02-核心流程.md)。
