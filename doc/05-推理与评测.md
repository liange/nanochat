# 05 - 推理与评测

本章详解 `nanochat/engine.py` 的 KV Cache 推理引擎与工具调用状态机、`scripts/infer_bench.py` 的推理成本基准，以及 base/chat 两套评测体系（CORE / bpb / ChatCORE）。

## 1. 推理引擎（`nanochat/engine.py`）

### 1.1 设计原则

- 引擎**只处理 token id 序列，不碰 prompt 渲染与 tokenization**（模块 docstring）。tokenization 由调用方（`chat_cli`/`chat_sft`/`chat_rl`/`chat_eval`/`infer_bench`）负责。引擎构造函数要拿到 tokenizer，用途有两个：**工具调用时 decode/encode 表达式**，以及**终止 token 判定**——`encode_special` 取 `<|assistant_end|>`、`get_bos_token_id()` 作为第二终止条件（源码注释只写了 `# needed for tool use`，实际用途略宽）。
- 基于 **KV cache** 做高效自回归生成，避免逐 token 全量重算。
- 生成有 **seed 可复现**；`temperature=0` 与 seed 无关地确定（`nanochat/engine.py#sample_next_token` 走 argmax 分支，不碰 rng）。
- **无投机解码**（speculative decoding / EAGLE 等全仓库均未实现）：逐 token 串行 decode。但 `cache_seqlens` 逐 batch 追踪、`advance(T)` 支持一次推进多 token 的设计，为未来扩展留了空间。
- 一致性守护是**三层**的，各覆盖不同面：
  1. `nanochat/engine.py` 末尾 `__main__` 的对拍自测：比对 `GPT.generate`（朴素路径）与 `Engine.generate` 逐 token 是否一致——**这是唯一验证 KV cache 前向与训练前向数值一致的机制**，但需要真实 checkpoint 且调 `torch.cuda.synchronize()`，CPU 上跑不了；
  2. `tests/test_attention_fallback.py`：FA3 与 SDPA 回退在 KV cache 下的等价性（prefill、单 token decode、**单 token + 滑窗 decode**——最后这个用例专门抓「SDPA 在 Tq=1 时忽略 window」的 bug），可在 CPU 上跑；
  3. `tests/test_engine.py`：采样语义（多样性、seed 可复现、temperature=0 确定性、max_tokens/num_samples）。**注意它全程用 MockModel**（均匀 logits、无真实 attention），**不验证 KV cache 数值一致性**。

### 1.2 `KVCache`（`nanochat/engine.py#KVCache`）

为 FA3 的 `flash_attn_with_kvcache` API 设计，**与 FA2 风格的 cache 有三处关键差异**（docstring 明列）：

| 项 | 说明 |
|----|------|
| 张量布局 | **`(n_layers, B, T, H, D)`**——注意 T 在 H 之前，这是 FA3 原生布局，不是 FA2 的 `(B,H,T,D)` |
| 更新方式 | **FA3 在 `flash_attn_with_kvcache` 内部原地更新 cache**；SDPA 回退也手动做同样的原地写入，保证语义一致 |
| 位置追踪 | 用 `cache_seqlens`（`(B,)` int32）逐 batch 元素记录位置 |

成员与接口：

- `k_cache` / `v_cache`：`(n_layers, B, T_max, n_kv_head, head_dim)`，构造时一次性预分配。
  **注意用 `n_kv_head` 而不是 `n_head`**——GQA 下 KV 头更少，cache 占比也随之下降。
- `cache_seqlens`：int32，FA3 要求这个 dtype。
- `prev_embedding`：smear 用的上一 token 归一化 embedding，**由模型 forward 写入**。这是 KV cache 里除 K/V 外的唯一额外状态。
- `reset()`：把 `cache_seqlens` 清零并丢弃 `prev_embedding`。
- `get_pos()`：返回当前位置（**假定所有 batch 元素位置相同**，所以只取 `[0]`）。
- `get_layer_cache(layer_idx)`：返回该层的 `(k_cache, v_cache)` 视图，attention 里按层取用。
- `advance(num_tokens)`：`cache_seqlens += num_tokens`。
- `prefill(other)`：把另一个 cache 的 KV 拷进来，用于「batch=1 预填 → 复制成多路并行采样」。它还会把 `prev_embedding` 从 `(1,1,C)` **expand 到 `(num_samples,1,C)` 并 clone**，否则多路采样的 smear 状态会串味。

> **dtype 现在的来源是 `COMPUTE_DTYPE`**（`nanochat/engine.py#Engine.generate` 里 `dtype = COMPUTE_DTYPE`），不再是「cuda→bf16 / 其他→fp32」的硬编码魔数。旧文档描述的 hack 已被移除；现在 cache 精度自动跟随训练精度（V100/T4 上是 fp32）。

### 1.3 `Engine.generate`（`nanochat/engine.py#Engine.generate`）

流式生成器，装饰器是 `@torch.inference_mode()`，三段式：

**① batch=1 预填 prompt**

```
ids = tokens 的 (1, T) 张量
kv_cache_prefill = KVCache(batch_size=1, seq_len=len(tokens), dtype=COMPUTE_DTYPE, ...)
logits = model.forward(ids, kv_cache=kv_cache_prefill)      # 全序列一次算完
logits = logits[:, -1, :].expand(num_samples, -1)           # 只取最后一个位置，广播到 num_samples
```

模型 forward 在最后一层调 `kv_cache.advance(T)`，所以预填后 `cache_seqlens == len(tokens)`。

**② 复制 KV cache 成 num_samples 路**

```
kv_length_hint = (len(tokens) + max_tokens) if max_tokens is not None else config.sequence_len
kv_cache_decode = KVCache(batch_size=num_samples, seq_len=kv_length_hint, ...)
kv_cache_decode.prefill(kv_cache_prefill)     # 含 prev_embedding 的 batch 展开
del kv_cache_prefill
```

注意 `kv_length_hint`：预分配长度是按**实际需要**估的（prompt + max_tokens），不是无脑开 `sequence_len`，省显存。

**③ 主循环**

```
row_states = [RowState(tokens.copy()) for _ in range(num_samples)]
while True:
    if max_tokens is not None and num_generated >= max_tokens: break   # 停条件 A
    if all(s.completed for s in row_states): break                     # 停条件 B

    next_ids = sample_next_token(logits, rng, temperature, top_k)      # (B,1)，一次采所有行
    token_column, token_masks = [], []
    for i, state in enumerate(row_states):
        is_forced  = len(state.forced_tokens) > 0
        token_masks.append(0 if is_forced else 1)                      # 0=forced, 1=sampled
        next_token = state.forced_tokens.popleft() if is_forced else sampled_tokens[i]
        token_column.append(next_token)
        state.current_tokens.append(next_token)
        if next_token in (assistant_end, bos): state.completed = True
        ...工具调用状态转移...
    yield token_column, token_masks
    num_generated += 1
    ids = tensor(token_column).unsqueeze(1)                            # (B,1)
    logits = model.forward(ids, kv_cache=kv_cache_decode)[:, -1, :]     # 一次 forward 推进所有行
```

关键设计：

- **每一行是一个独立序列，但共享同一次 forward**。`num_samples` 条采样被打包成一个 batch，KV cache 是 `num_samples` 路，所以并行采样几乎免费（直到显存或计算饱和）。
- **采样是按行独立做的**（`sample_next_token` 作用在整个 `(B,1)` logits 上，multinomial 逐元素），但 rng 是同一个 `torch.Generator`，所以整批的随机流是可复现的。
- **forced token 会盖掉采样结果**，并把该位置 mask 标为 0。这是工具调用能被正确 mask 的机制基础。
- **停条件是「或」关系**：达到 max_tokens 或所有行都完成。**行完成后其 token 仍会被 yield**（因为 forward 需要等长张量），只是 `generate_batch` 会过滤掉完成行之后的内容。

### 1.4 工具调用状态机（`nanochat/engine.py#RowState`）

每条采样序列一个 `RowState`，字段：

| 字段 | 含义 |
|------|------|
| `current_tokens` | 当前完整序列 |
| `forced_tokens` | `deque`，待强制注入的 token 队列（工具输出） |
| `in_python_block` | 是否在 `<|python_start|>...<|python_end|>` 内 |
| `python_expr_tokens` | 累积的表达式 token |
| `completed` | 是否遇到 `<|assistant_end|>` 或 `<|bos|>` |

状态转移（在主循环的 per-row 分支里）：

```
遇到 <|python_start|>  → in_python_block = True, 清空 python_expr_tokens
在块内遇到普通 token   → append 到 python_expr_tokens
遇到 <|python_end|>（且 in_python_block）→ 退出块
    若 python_expr_tokens 非空（空表达式守卫，不求值不注入）：
        expr   = tokenizer.decode(python_expr_tokens)
        result = use_calculator(expr)
        若 result is not None:
            forced_tokens 依次入队 <|output_start|> + encode(str(result)) + <|output_end|>
```

- **工具输出 token 是 forced（mask=0）**，不会进入 loss —— RL 训练时正是靠这个 mask 区分「模型生成的 token」与「环境注入的 token」（`scripts/chat_rl.py` 里 target 置 -1 的位置与此对应）。
- 若 `use_calculator` 返回 `None`（表达式非法或求值出错），**不注入任何 output**，模型继续自由生成——工具失败不会让引擎崩溃。
- forced token 走同样的 state 转移逻辑（比如 forced 的 `<|output_start|>` 不会触发 python 块，因为它不等于 `python_start`），所以不会递归触发工具。

### 1.5 `sample_next_token`（`nanochat/engine.py#sample_next_token`）

三条路径，`@torch.inference_mode()`：

| 条件 | 行为 |
|------|------|
| `temperature == 0.0` | `argmax`（确定性，**不使用 rng**，所以换 seed 结果不变） |
| `top_k > 0` | 先 `torch.topk` 取 k 个，**只在这 k 个上缩温 softmax 再 multinomial**，最后用 `idx.gather` 映射回真实 token id |
| 否则 | 全词表 `logits/temperature` → softmax → multinomial |

- `k = min(top_k, vocab_size)`，所以 `top_k` 大于词表也不会报错。
- 有 `assert temperature >= 0.0`：负温度会明确报错而不是产生 NaN。

### 1.6 计算器工具（`nanochat/engine.py#use_calculator`）

模型在 `<|python_start|>...<|python_end|>` 里写表达式，引擎安全求值。**两条互斥的白名单路径**：

**路径 A —— 纯数学表达式**：全部字符都在 `"0123456789*+-/.() "` 内

- 先 `expr.replace(",", "")` 去掉千分位逗号；
- **显式禁止 `**`**（幂运算），因为它会让表达式爆炸式增长（`2**999999999`）；
- 通过 `eval_with_timeout` 求值。

**路径 B —— 字符串操作**：字符都在 `abcdefghijklmnopqrstuvwxyzABC...0123456789'"()._ ` 内

- 小写后检查黑名单：`__`、`import`、`exec`、`eval`、`compile`、`open`、`file`、`input`、`raw_input`、`globals`、`locals`、`vars`、`dir`、`getattr`、`setattr`、`delattr`、`hasattr`；
- **必须包含 `.count(`**，否则返回 `None`（只放开这一种方法，源码注释说明后续再扩展）；
- 同样走 `eval_with_timeout`。

超时保护在 `nanochat/engine.py#eval_with_timeout`：用 `signal.signal(SIGALRM, ...)` + `signal.alarm(duration)` 设 3 秒（`nanochat/engine.py#timeout` 是它的上下文管理器，退出时 `signal.alarm(0)` 取消），超时抛异常被捕获返回 `None`。

> 这是 GSM8K 工具调用（`<<12/60=0.2>>`）的推理期实现。训练期工具输出由数据给出（`tasks/gsm8k.py` 解析），推理期由计算器算出。**两条路径都必须产出与训练数据同分布的 output 文本**，否则模型看到的是分布外输入。

### 1.7 `generate_batch`（`nanochat/engine.py#Engine.generate_batch`）

非流式封装，用于 RL rollout 与评测：

```
results = [tokens.copy() for _ in range(num_samples)]   # 从 prompt 开始
masks   = [[0]*len(tokens) for _ in range(num_samples)] # prompt 部分 mask=0
completed = [False]*num_samples
for token_column, token_masks in self.generate(tokens, num_samples, **kwargs):
    for i, (token, mask) in enumerate(zip(token_column, token_masks)):
        if not completed[i]:
            if token in (assistant_end, bos): completed[i] = True     # 终止 token 不计入
            else: results[i].append(token); masks[i].append(mask)
    if all(completed): break
return results, masks
```

- **返回的序列含 prompt 前缀**（`results` 从 `tokens.copy()` 起），不只是新生成的 token。
- **终止 token 本身不计入**结果。
- **prompt 部分的 mask 一律是 0**，与 forced token 一致——这正是 RL 里 target 置 -1 的依据。
- 已在某轮完成的行走后续轮次不再追加（但 forward 仍在算，因为张量要等长）。

### 1.8 推理期的性能特征

理解 `infer_bench` 的读数需要这个背景（`scripts/infer_bench.py` 模块 docstring 有展开）：

- **Prefill** 把整段 prompt 并行处理：大 matmul、**compute-bound**，用 **MFU** 衡量离 roofline 的距离。
- **Decode** 每步只生成 1 个 token，却必须**重读全部权重 + KV cache**才能做一点点数学，所以是 **memory-bandwidth-bound**。因此：
  - batching **几乎免费**直到 compute 饱和——这正是 `num_samples` 并行采样高效的物理原因；
  - `temperature=0`（argmax）**不读额外数据**，比采样路径略快；
  - **GQA 与滑动窗口的直接收益就在这里**：GQA 减少 KV 头数 → `kv_bytes_per_token` 变小；滑窗让 `kv_read_bytes(ctx)` 在长上下文下被 `window` 封顶。
- **TTFT**（time to first token）≈ prefill 时间；**TPOT**（time per output token）≈ 一次 decode step 时间。

### 1.9 推理期的 RoPE 增量与 smear 分支

KV cache 一致性的两个容易漏的细节（都在 `nanochat/gpt.py#GPT.forward`）：

- **RoPE 位置偏移**：forward 开头取 `T0 = kv_cache.get_pos()`，从预计算的 cos/sin 表上截 `[T0 : T0+T]`——decode 步的位置不是 0，而是接在已有 KV 之后。rotary 表预计算到 `sequence_len * 10` 的余量（支持超过训练长度的长生成），越界时 `assert T <= cos.size(1)` 明确报错。
- **smear 的双分支**：`T > 1`（prefill）走整段切片 `x[1:] += gate * x[:-1]`；`T == 1`（decode）从 `kv_cache.prev_embedding` 读上一 token 的 embedding；且 decode 首步 `prev_embedding` 为 `None` 时直接跳过 smear 项。**修改 smear 时 prefill 与 decode 两条分支都要同步**——这正是 §1.2 强调 `prefill()` 要展开 `prev_embedding` 的原因。

## 2. Base 模型评测（`scripts/base_eval.py` + `nanochat/core_eval.py` + `nanochat/loss_eval.py`）

三种模式：`core` / `bpb` / `sample`，默认全跑。

### 2.1 CORE 指标（DCLM 论文）

入口 `scripts/base_eval.py#evaluate_core`：

1. 下载并解压 `eval_bundle.zip`（含 `core.yaml` 配置、`eval_data/` 各任务 jsonl、`eval_meta_data.csv` 随机基线，`scripts/base_eval.py#place_eval_bundle`）。
2. 对 `core.yaml` 里每个 ICL 任务：
   - 按 `task_type`（`multiple_choice` / `schema` / `language_modeling`）渲染 prompt（`nanochat/core_eval.py#render_prompts_mc` / `#render_prompts_schema` / `#render_prompts_lm`），含 few-shot 示例；
   - 定位 continuation 起止（公共前缀/后缀，`nanochat/core_eval.py#find_common_length`）；
   - `forward_model` 算每位置 loss 与 argmax（`nanochat/core_eval.py#forward_model`）；
   - 判分：MC/schema 取最低平均 loss 的选项，LM 看 argmax 是否全对（`nanochat/core_eval.py#evaluate_example`）。
3. **centered 归一化**（在 `evaluate_core` 内）：

   ```
   centered = (accuracy - 0.01 * random_baseline) / (1 - 0.01 * random_baseline)
   ```

   **注意 `0.01` 这个因子**：csv 里的 `Random baseline` 是百分数（如 25 表示 25%），所以要乘 0.01 换成比例。漏掉它会得到一个几乎恒等于 accuracy 的假 CORE。
4. **CORE = 各任务 centered 的均值**。
5. 每个任务的样本会 `shuffle`（固定 `random.Random(1337)`）后按 rank 分派，最后 `all_reduce` 汇总。
6. `--max-per-task` 可限制每任务样本数以快速试跑。

> GPT-2 (1.6B) 的 CORE 是 **0.256525**，这是 speedrun 要超越的目标（`README.md#Time-to-GPT-2 Leaderboard`）。
>
> ⚠️ `nanochat/core_eval.py` 的 docstring 自述 squad 任务与参考值仍有差距（31% vs 37%），属已知 TODO。

### 2.2 bpb（bits-per-byte）

`nanochat/loss_eval.py#evaluate_bpb`：

- `model(x, y, loss_reduction='none')` 得逐 token loss；
- 按 `token_bytes`（每 token 的 UTF-8 字节数）加权求和 nats 与 bytes；特殊 token（bytes=0）与 mask 位（target<0）不计；
- 跨 rank `all_reduce` 总 nats 与总 bytes；
- `bpb = total_nats / (ln2 * total_bytes)`。
- **与词表大小无关**，换 tokenizer 仍可比（前提是数据不变）。

### 2.3 采样

条件采样（一组固定 prompt）+ 无条件采样（BOS 起，温度 1.0，8 条），用 `Engine.generate_batch`。

### 2.4 关于外部模型

当前 `base_eval.py` **只支持 nanochat 自己的 checkpoint**。旧版本的 `--hf-path` / `ModelWrapper` / `load_hf_model` 与 `HuggingFaceTokenizer` 一起被删除了，所以无法用同一套 CORE/bpb 去评外部模型。

## 3. Chat 模型评测（`scripts/chat_eval.py`）

**5 个任务**，分两类。

### 3.1 Categorical 评测（`scripts/chat_eval.py#run_categorical_eval`）

ARC-Easy / ARC-Challenge / MMLU。**无需采样**：

1. 每题用 `render_for_completion` 渲染 prompt（用 `render_for_completion` 而非 `render_conversation`，因为它会自动追加 `<|assistant_start|>`，答案位置就在序列末尾）；
2. 按 batch 内最长序列 pad，**pad token 用 BOS**（这些位置的结果被忽略）；
3. `answer_time_positions[i] = len(prompt) - 1` 记录每题答案所在的**最后一个位置**；
4. 一次 forward 得 `(B, T, V)` logits；
5. 对每题，**只在可选答案字母对应的 token id 上取 argmax**——这比让模型生成字母再判更简单可靠，源码注释也承认这**降低了任务难度**，但这是评测的标准做法；

   ```
   focus_logits = logits[idx, answer_pos, letter_ids]      # 只在 4 个 (或 N 个) 字母上比
   predicted_letter = letters[focus_logits.argmax()]
   ```
6. `letter_to_id_cache` 缓存字母→token id 映射省 tokenizer 调用，并 `assert len(encoded_letter) == 1`（**每个选项字母必须是单 token**，否则整个策略不成立）；
7. 跨 rank 用 `all_reduce(SUM)` 汇总 passed/total，按 batch 交错分派（`range(ddp_rank, num_batches, ddp_world_size)`）。

> 多选题渲染用 `tasks/common.py#render_mc`：字母在选项**之后**、`=` 与字母间无空格，专为小模型 token 对齐设计。

### 3.2 Generative 评测（`scripts/chat_eval.py#run_generative_eval`）

GSM8K / HumanEval。逐题采样：

1. `render_for_completion` → `engine.generate_batch` 采样 `num_samples` 条；
2. decode 后调 `task.evaluate(conversation, completion)` 判分；
3. `passed = any(outcomes)`（pass@k 语义：k 条里有一条对就算过）；
4. 跨 rank 汇总。

- **HumanEval**：`task.evaluate` 内部用 `nanochat/execution.py` 沙箱执行生成代码并跑测试（`tasks/humaneval.py`）。沙箱移植自 OpenAI human-eval 的 execution.py：**每段代码独立子进程**、父进程超时（默认 5 秒）硬杀、subprocess guard 黑名单（`os.system` / `os.kill` / `shutil.rmtree` / `subprocess.Popen` 等）、内存 rlimit 256MB。注意它与 §1.6 的 `eval_with_timeout`（SIGALRM + 字符白名单，跑计算器表达式）是**两套不同的执行机制**，不要混淆。
- **GSM8K**：从回答里抽 `#### 数字` 比对（`tasks/gsm8k.py#GSM8K.evaluate`）。
- 生成式任务的温度由 `-t/--temperature` 控制（默认 0.0）。

### 3.3 ChatCORE（`scripts/chat_eval.py` __main__ 段 与 `scripts/chat_sft.py:ChatCORE`）

```
baseline = { ARC-Easy: 0.25, ARC-Challenge: 0.25, MMLU: 0.25, GSM8K: 0.0, HumanEval: 0.0 }
centered_acc = (acc - baseline) / (1 - baseline)
ChatCORE = mean(centered_acc over 5 tasks)
```

范围 0（随机）→ 1（完美）。

- **只在 5 个任务全部被评估时才算**（`all_tasks_were_evaluated`），所以 `chat_eval.py -a ARC-Easy` 这种单任务跑法不会打印 ChatCORE。
- SFT 训练中周期算时**额外记录 `chatcore_cat`**（只对 3 个 categorical 任务求 centered mean），因为它收敛更快、更适合当训练信号。
- SFT 训练中的 ChatCORE 可以用 `--chatcore-max-cat` / `--chatcore-max-sample` 限制样本数（-1 表示不限）。
- **旧文档说的「6 个任务」是错的**——SpellingBee 在当前仓库不存在。

## 4. RL 中的评测（`scripts/chat_rl.py`）

- **pass@k**：在 GSM8K test 上，对每题采 `device_batch_size` 条，统计 k=1..device_batch_size 的 pass@k（前 k 条至少 1 条对）。`--eval-examples` 默认 400 题。
- `--eval-every` 默认 60 步评估一次。
- 跨 rank `all_reduce` 记录数与通过数。
- **RL 评估用温度 1.0**；训练 rollout 也用温度 1.0 + top-k=50（`--temperature` / `--top-k`）。
- 记录 `reward`（平均奖励）与平均序列长度到 wandb，reward 均值用 `all_reduce(AVG)` 跨 rank 对齐。

## 5. 推理基准（`scripts/infer_bench.py`）

这是**「智能指标」之外的第二根轴**：CORE 高不代表推理便宜。架构选择（GQA、滑窗）在 CORE 上几乎看不见，但在这里很明显，所以改动可以同时对两个轴评估。

### 5.1 两种 regime 与两个 roofline

| Regime | 特征 | 瓶颈 | 度量 |
|--------|------|------|------|
| **Prefill** | 整段 prompt 并行，大 matmul | compute-bound | **MFU** = `prefill_flops / time / peak_flops` |
| **Decode** | 每步 1 token，重读全部权重 + KV | bandwidth-bound | **MBU** = `(权重字节 + B·kv_read) / tpot / peak_bandwidth` |

**MBU 是 decode 侧的 MFU 对偶**：achieved bytes/sec 除以显存峰值带宽，衡量实现离物理上限有多远。

- **batch 1 的 decode 吞吐上限**：`peak_bw / (权重字节 + kv_read)`——每一步至少要搬这么多字节，这是硬下限。
- **batching 几乎免费**直到 compute 饱和，所以 sweep 会看到「tok/s 随 batch 近乎线性上升，直到某个点拐平」。
- **decode 的 MFU 极小**（源码注释说「keep the signal」，保留 4 位小数），别拿它跟训练 MFU 比。

### 5.2 静态卡片（测量之前就能算的架构账）

```
peak_bw, peak_flops, total_vram  = 查表 / 设备属性
w_bytes   = Σ p.numel() * p.element_size()           # decode 每步都要读
kv_store  = model.kv_bytes_per_token()
context_mid = prompt_len + decode_tokens // 2         # 代表性 decode 上下文
kv_read   = model.kv_read_bytes(context_mid)
ceiling_bs1 = peak_bw / (w_bytes + kv_read)           # batch 1 理论 tok/s 上限
max_rows  = (total_vram - w_bytes) / (kv_store * sequence_len)   # VRAM 能放多少全上下文行
```

打印内容含参数 dtype 分布（bf16/fp32 各多少）、权重字节、KV 字节/token、KV 读取/step、理论上限、最大行数。

### 5.3 测量方法

`bench_generate`（`scripts/infer_bench.py#bench_generate`）的技巧是**用生成器的时间点切分 TTFT 与 TPOT**：

```
generator = engine.generate(prompt, num_samples=batch_size, max_tokens=decode_tokens, ...)
t_start = perf_counter()
next(generator)              # 首次 next 完成：batch=1 prefill + KV 复制 + 采第一个 token
torch.cuda.synchronize(); ttft = perf_counter() - t_start      # ← TTFT
while True:
    t0 = perf_counter(); next(generator); synchronize()
    step_times.append(perf_counter() - t0)                      # ← 每个后续 next 是一次 decode step
```

- **必须 `torch.cuda.synchronize()`**，否则测的是内核入队时间而不是执行时间。
- `tpot` 取 `sorted(step_times)[n//2]`(**中位数**)而不是均值，避开偶发调度抖动。
- 每个配置**先跑一次 warmup**（cublas autotune、allocator warm、attention kernel 首次编译），再计时。
- 用真实自然语言 prompt（重复一段科普文本后截断）而不是随机 id，因为 `temperature=0` 的 argmax 在随机输入上会迅速退化。
- prompt 会被 clamp 到 `sequence_len - decode_tokens` 以保证 prompt+decode 不越界。

### 5.4 输出契约

- stdout 依次是：静态卡片、prefill 一行、表头 + 每个 batch size 一行、分隔线，**最后一行是一个完整 JSON**。
- 机器消费方式（模块 docstring 给的例子）：

  ```
  python -m scripts.infer_bench -i base -g d12 | tail -1 | jq .sweep
  ```
- JSON 字段：`source` / `step` / `model_config` / `gpu` / `peak_bandwidth_bytes_per_sec` / `peak_flops_per_sec` / `total_vram_bytes` / `num_params` / `param_dtypes` / `weight_bytes` / `kv_bytes_per_token` / `kv_read_bytes_per_step` / `context_mid` / `decode_flops_per_token` / `ceiling_bs1_tok_per_sec` / `max_full_context_rows` / `prompt_tokens` / `decode_tokens` / `temperature` / `prefill{tok_per_sec, mfu_percent, time_sec}` / `sweep[{batch_size, ttft_sec, tpot_sec, tok_per_sec, mbu_percent, mfu_percent, peak_vram_bytes, decode_steps}]`。
- **未知 GPU 的峰值带宽/flops 会序列化成 `null` 而不是 `Infinity`**，保证末行始终是合法 JSON。

### 5.5 使用示例

```bash
python -m scripts.infer_bench -i base -g d12                              # 默认扫 1,8,32,128
python -m scripts.infer_bench -i sft --batch-sizes 1,4,16,64 --decode-tokens 512
python -m scripts.infer_bench -i base -g d12 | tail -1 | jq .sweep
```

限制：**只支持 CUDA 单卡**（源码里对 `device_type == "cuda"` 与 `ddp_world_size == 1` 有 assert），因为要测 `torch.cuda` 计时与 VRAM。

## 6. 评测与推理的一致性要点

1. **KV cache 路径必须与训练前向同步**：修改 `GPT.forward` 的 attention / rotary / smear / value residual 任一处，都要同步 `CausalSelfAttention` 的 `kv_cache` 分支、`KVCache.prev_embedding` 的读写、以及 `advance` 的调用时机，否则推理与训练不一致（守护机制见 §1.1 的三层清单；数值一致性靠 `engine.py` 的 `__main__` 对拍）。
2. **`prev_embedding` 是第三个状态**：除了 K/V，smear 还需要上一 token 的 embedding。多路采样时必须 `expand(...).clone()` 复制，否则各路之间会互相污染。最容易漏的一处。
3. **滑动窗口在推理期也生效**：`window_sizes` 训练和推理共用同一份 `_compute_window_sizes`。SDPA 回退的滑窗实现走显式 bool mask，因为 `is_causal` 在 `Tq != Tk`（chunked decode）时对不齐 cache 位置。
4. **工具调用 token 的 mask**：forced token（工具输出）mask=0，不进 loss；这是 RL 能正确区分「自生成」与「环境注入」的基础。
5. **dtype 一致**：KV cache 与 rotary 都用 `COMPUTE_DTYPE`；CPU/MPS 上 checkpoint 会把 bf16 权重转 fp32（`nanochat/checkpoint_manager.py`）。categorical 评测则依赖**选项字母必须是单 token**（有 assert 守）。
6. **seed 可复现**：`Engine.generate` 的 `seed` 控制 `torch.Generator`；`temperature=0` 走 argmax，**与 seed 无关**。RL rollout 每批换 seed（`hash((step, example_idx, sampling_step))`）以保证样本多样。
