# 05 - 推理与评测

本章详解 `nanochat/engine.py` 的 KV Cache 推理引擎与工具调用状态机，以及 base/chat 两套评测体系（CORE / bpb / ChatCORE）。

---

## 1. 推理引擎（`nanochat/engine.py`）

### 1.1 设计原则

- 引擎**只处理 token id 序列，不碰 tokenization**（`engine.py:9`）。tokenization 由调用方（`chat_cli`/`chat_sft`/`chat_rl`/`chat_eval`）负责。
- 基于 **KV cache** 做高效自回归生成，避免逐 token 全量重算。
- 生成有 **seed 可复现**；`temperature=0` 与 seed 无关地确定（`engine.py:141`）。
- 仓库有对照测试守住「训练前向与 KV cache 推理一致」（`engine.py:307` 的 `__main__` 比对 `model.generate` 与 `Engine.generate`）。

### 1.2 `KVCache`（`engine.py:82`）

为 FA3 的 `flash_attn_with_kvcache` API 设计：

- 张量布局是 **`(B, T, H, D)`**（FA3 原生，非 FA2 的 `(B,H,T,D)`）；
- 预分配 `k_cache` / `v_cache`：`(n_layers, B, T_max, H_kv, D)`（`engine.py:99`）；
- `cache_seqlens`：`(B,)` int32，记录每条 batch 元素的当前位置（FA3 需要，`engine.py:102`）；
- `prev_embedding`：smear 用的上一 token embedding，由模型 forward 写入（`engine.py:104`）；
- `prefill(other)`（`engine.py:123`）：把另一个 cache 的 KV 拷过来，用于「batch=1 预填 → 复制成多路并行采样」，并展开 `prev_embedding`（`engine.py:136`）；
- `advance(num_tokens)`（`engine.py:119`）：推进位置；注意**只有最后一层处理完才 advance**（由 `CausalSelfAttention.forward` 负责，`gpt.py:120`）。

> dtype 硬编码：cuda→bf16，其余→fp32（`engine.py:186`，注释承认这是个待重构的 hack）。

### 1.3 `Engine.generate`（`engine.py:176`）

流式生成器，三段式：

```
1) batch=1 预填 prompt → 得首 token logits
2) 把 KV cache 复制成 num_samples 路
3) 主循环：
   while 未到 max_tokens 且未全部完成:
     sample_next_token(logits, rng, temp, top_k)   # (B,1)
     逐行处理：选 token（forced 或 sampled）、更新状态、工具调用
     yield (token_column, token_masks)              # masks: 0=forced, 1=sampled
     ids = token_column → model.forward(ids, kv_cache) → 下一轮 logits
```

### 1.4 工具调用状态机（`RowState`，`engine.py:160`）

每条采样序列一个 `RowState`，维护：

- `current_tokens`：当前序列；
- `forced_tokens`：待强制注入的 token 队列（工具输出）；
- `in_python_block` / `python_expr_tokens`：是否在 python 块、累积的表达式 token；
- `completed`：是否遇到 `<|assistant_end|>` 或 `<|bos|>`。

状态转移（`engine.py:257`）：

```
遇到 <|python_start|> → 进入 python 块，清空 expr
  块内每个 token → 累积到 python_expr_tokens
遇到 <|python_end|>（且在块内）→ 退出块
  expr = tokenizer.decode(python_expr_tokens)
  result = use_calculator(expr)        # 安全求值
  若 result 非空: forced_tokens 队列注入 <|output_start|> + result_tokens + <|output_end|>
遇到 <|assistant_end|>/<|bos|> → 标记完成
```

关键点：**工具输出 token 是 forced（mask=0）**，不会进入 loss —— RL 训练时正是靠这个 mask 区分「模型生成的 token」与「环境注入的 token」（`chat_rl.py:139`）。

### 1.5 `sample_next_token`（`engine.py:141`）

- `temperature=0`：直接 argmax（确定性）；
- `top_k>0`：先取 topk，缩温后 softmax 再 multinomial（只在 k 个里采）；
- 否则：全词表 softmax + multinomial。

### 1.6 计算器工具（`use_calculator`，`engine.py:46`）

模型在 `<|python_start|>...<|python_end|>` 里写表达式，引擎用 `use_calculator` 安全求值：

- 纯数学表达式（仅数字与 `+-/.()`，禁 `**` 幂）→ `eval`（清空 builtins，超时保护）；
- 字符串 `.count()` 操作（如 `'strawberry'.count('r')`）→ 同样受限 eval；
- 黑名单：`__`、`import`、`exec`、`eval`、`open` 等危险模式一律拒绝（`engine.py:67`）。

> 这是 GSM8K 工具调用（`<<12/60=0.2>>`）的推理期实现。训练期工具输出由数据给出，推理期由计算器算出。

### 1.7 `generate_batch`（`engine.py:282`）

非流式封装：跑完 `generate` 收集最终序列，去掉终止 token（`assistant_end`/`bos`），返回 `(results, masks)`。RL roll-out 与评测都用它。

## 2. Base 模型评测（`scripts/base_eval.py` + `nanochat/core_eval.py` + `nanochat/loss_eval.py`）

三种模式（`base_eval.py:180`）：`core` / `bpb` / `sample`，默认全跑。

### 2.1 CORE 指标（DCLM 论文）

入口 `evaluate_core`（`base_eval.py:107`）：

1. 下载并解压 `eval_bundle.zip`（含 `core.yaml` 配置、各任务 jsonl、随机基线 csv，`base_eval.py:92`）。
2. 对 `core.yaml` 里每个 ICL 任务（`base_eval.py:124`）：
   - 按 `task_type`（`multiple_choice` / `schema` / `language_modeling`）渲染 prompt（`core_eval.py:17/36/56`），含 few-shot 示例；
   - 定位 continuation 起止（公共前缀/后缀，`core_eval.py:86`）；
   - `forward_model` 算每位置 loss 与 argmax（`core_eval.py:144`）；
   - 判分：MC/schema 取最低平均 loss 的选项，LM 看 argmax 全对（`core_eval.py:224`）。
3. **centered 归一化**（`base_eval.py:162`）：`(accuracy - random_baseline) / (1 - random_baseline)`。
4. **CORE = 各任务 centered 的均值**（`base_eval.py:167`）。

> GPT-2 (1.6B) 的 CORE 是 0.256525，这是 speedrun 要超越的目标（`README.md:24`）。

### 2.2 bpb（bits-per-byte）

`evaluate_bpb`（`loss_eval.py:9`）：

- `model(x, y, loss_reduction='none')` 得逐 token loss；
- 按 `token_bytes`（每 token 的 UTF-8 字节数）加权求和 nats 与 bytes；特殊 token（bytes=0）与 mask 位（target<0）不计；
- 跨 rank all_reduce；`bpb = total_nats / (ln2 * total_bytes)`（`loss_eval.py:64`）。
- **与词表大小无关**，换 tokenizer 仍可比（前提是数据不变）。

### 2.3 采样

条件采样（一组固定 prompt）+ 无条件采样（BOS 起，温度 1.0，8 条），用 `Engine.generate_batch`（`base_eval.py:241`）。

### 2.4 HuggingFace 模型支持

`--hf-path openai-community/gpt2` → `load_hf_model`（`base_eval.py:67`）用 `ModelWrapper`（`base_eval.py:45`）适配 nanochat 接口，可用同一套 CORE/bpb 评测外部模型。

## 3. Chat 模型评测（`scripts/chat_eval.py`）

6 个任务（`chat_eval.py:204`），分两类：

### 3.1 Categorical 评测（`run_categorical_eval`，`chat_eval.py:88`）

ARC-Easy / ARC-Challenge / MMLU。无需采样：

1. 批量 `render_for_completion` 渲染 prompt，pad 到等长（用 BOS pad，`chat_eval.py:110`）；
2. 一次 forward 得 `(B, T, V)` logits；
3. 对每题，只在**可选答案字母**对应的 token id 上取 argmax（`chat_eval.py:133`）—— 这比让模型生成字母再判更简单可靠；
4. 缓存 letter→token_id 映射省 tokenizer 调用（`chat_eval.py:126`）；
5. 跨 rank `all_reduce(SUM)` 汇总。

> 多选题渲染用 `tasks/common.py:112` 的 `render_mc`：字母在选项**之后**、`=` 与字母间无空格，专为小模型 token 对齐设计。

### 3.2 Generative 评测（`run_generative_eval`，`chat_eval.py:29`）

GSM8K / HumanEval / SpellingBee。逐题采样：

1. `render_for_completion` → `engine.generate_batch` 采样 `num_samples` 条；
2. decode 后调 `task.evaluate(conversation, completion)` 判分；
3. `passed = any(outcomes)`（pass@k）；
4. 跨 rank 汇总。

- **HumanEval**：`task.evaluate` 内部用 `execution.py` 沙箱执行生成的代码并跑测试（`tasks/humaneval.py`）。
- **GSM8K**：从回答里抽 `#### 数字` 比对（`tasks/gsm8k.py:23`）。
- **SpellingBee**：拼写/数字母任务。

### 3.3 ChatCORE（`chat_eval.py:238`）

```
centered_acc = (acc - baseline) / (1 - baseline)    # baseline: 多选题 0.25，生成题 0
ChatCORE = mean(centered_acc over 6 tasks)
```

范围 0（随机）→1（完美）。SFT 训练中也会周期性算 ChatCORE（`chat_sft.py:366`）。

## 4. RL 中的评测（`scripts/chat_rl.py`）

- **pass@k**（`chat_rl.py:225`）：在 GSM8K test 上，对每题采 `device_batch_size` 条，统计 k=1..device_batch_size 的 pass@k（前 k 条至少 1 条对）。
- 跨 rank `all_reduce(SUM)` 记录数与通过数（`chat_rl.py:233`）。
- RL 评估用温度 1.0（`chat_rl.py:228`），训练 roll-out 也用温度 1.0 + top-k=50。

---

## 5. 评测与推理的一致性要点

1. **KV cache 路径必须与训练前向同步**：修改 `GPT.forward` 的 attention / rotary / smear / value residual 等任一处，都要同步 `CausalSelfAttention` 的 `kv_cache` 分支与 `KVCache` 的 `prev_embedding`/`advance` 调用，否则推理与训练不一致（仓库有对照测试守住，`engine.py:307`）。
2. **滑动窗口在推理期也生效**：`window_sizes` 在训练和推理都用同一份 `_compute_window_sizes`（`gpt.py:285`）。
3. **工具调用 token 的 mask**：forced token（工具输出）mask=0，不进 loss；这是 RL 能正确区分「自生成」与「环境注入」的基础（`chat_rl.py:139`）。
4. **dtype 一致**：推理 KV cache 用 cuda→bf16 / 否则 fp32（`engine.py:186`），与训练 `COMPUTE_DTYPE` 一致；CPU/MPS 上 checkpoint 会把 bf16 权重转 fp32（`checkpoint_manager.py:87`）。
5. **seed 可复现**：`Engine.generate` 的 `seed` 控制 `torch.Generator`；`temperature=0` 走 argmax 与 seed 无关（`engine.py:141`）。
